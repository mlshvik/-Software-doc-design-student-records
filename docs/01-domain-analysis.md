# 1. Аналіз предметної області

**Проєкт 16 – Система обліку студентів у ВНЗ**
Дисципліна: «Документування програмного забезпечення та шаблони проектування»
Виконала: Маліш Вікторія, група ІР-43

## 1.1. Опис предметної області

Заклад вищої освіти складається з **факультетів**. Кожен факультет готує студентів за
кількома **спеціальностями** (наприклад, 126 «Інформаційні системи та технології»).
Студенти однієї спеціальності, одного року вступу об'єднуються в **академічні групи**
(наприклад, ІР-43), які навчаються на певному **курсі** (1–6).

Кожен семестр групі призначається набір **дисциплін** (предметів). Дисципліна має кількість
кредитів ЄКТС, кількість годин і форму підсумкового контролю: **іспит**, **залік** або
**диференційований залік**. Кожну дисципліну в конкретній групі в конкретному семестрі веде
**викладач** – це «призначення викладача» (навантаження).

Під час сесії викладач виставляє **оцінки** за 100-бальною шкалою. Оцінка автоматично
переводиться в національну шкалу («відмінно», «добре», «задовільно», «незадовільно» /
«зараховано», «не зараховано») та шкалу ЄКТС (A, B, C, D, E, FX, F).

Оцінка нижче 60 балів (або відсутність оцінки після закінчення сесії) утворює
**академічну заборгованість**. Студент має право на дві перескладання: перше – викладачу,
друге – комісії. Після успішного перескладання заборгованість закривається.

Для кожного студента система автоматично розраховує **середній бал** (за семестр і загальний).
Підтримуються два способи розрахунку: просте середнє арифметичне та середнє, зважене на
кількість кредитів ЄКТС (використовується для рейтингу стипендій).

Студент перебуває в одному зі **статусів**: навчається, академічна відпустка, відрахований,
випускник. Від статусу залежить, які дії над ним дозволені (наприклад, не можна виставити
оцінку відрахованому студенту).

Деканат (адміністратор) формує **розклад занять**: для кожного призначення викладача задаються
день тижня, номер пари, тип тижня (щотижня / чисельник / знаменник), аудиторія і тип заняття
(лекція, практичне, лабораторне).

## 1.2. Актори системи

| Актор | Опис |
|---|---|
| **Гість** | Неавторизований користувач. Може увійти в систему та переглянути загальний розклад груп. |
| **Студент** | Переглядає свої оцінки, середній бал, академічні заборгованості, розклад, сповіщення. |
| **Викладач** | Переглядає свої групи й дисципліни, виставляє оцінки та перескладання, переглядає свою статистику та розклад. |
| **Адміністратор (деканат)** | Керує довідниками (факультети, спеціальності, групи, предмети), студентами та викладачами, призначає викладачів, формує розклад, змінює статус студентів, формує звіти, налаштовує систему. |

## 1.3. Функціональні вимоги

**FR-1. Облік студентів.** Створення, редагування, пошук, фільтрація студентів за факультетом,
спеціальністю, групою, курсом; зміна статусу студента; переведення в іншу групу.

**FR-2. Облік викладачів і предметів.** CRUD викладачів (ПІБ, посада, науковий ступінь, кафедра)
та дисциплін (назва, кредити, години, форма контролю). Призначення викладача на дисципліну в групі
на семестр.

**FR-3. Фіксація оцінок.** Викладач вносить оцінку (0–100) за іспит / залік лише для своїх
призначень. Валідація: діапазон балів, активний статус студента, ліміт спроб (основна + 2
перескладання). Автоматичне перетворення в національну шкалу та ЄКТС.

**FR-4. Середній бал.** Автоматичний перерахунок середнього балу студента при кожній зміні оцінок
(семестровий та загальний), вибір стратегії розрахунку в налаштуваннях.

**FR-5. Академічна заборгованість.** Автоматичне відкриття заборгованості при незадовільній оцінці,
закриття при успішному перескладанні, перегляд списку боргів студента / групи.

**FR-6. Розклад занять.** Формування розкладу групи з перевіркою конфліктів (викладач, аудиторія
або група вже зайняті в цей час), перегляд розкладу групи, викладача, студента.

**FR-7. Звіти.**
- успішність студентів за групами та курсами;
- статистика по викладачах (середні оцінки студентів);
- звіт про академічні борги.

**FR-8. Сповіщення.** Студент отримує сповіщення про нову оцінку та про відкриту / закриту
заборгованість.

**FR-9. Автентифікація та ролі.** Вхід за логіном і паролем, розмежування доступу за ролями
ADMIN, TEACHER, STUDENT.

## 1.4. Нефункціональні вимоги

- Веб-додаток з архітектурою клієнт–сервер; взаємодія через **REST API** (JSON).
- Дані зберігаються в реляційній БД **PostgreSQL**, схема версіонується міграціями Flyway.
- Бекенд – Java 17, Spring Boot 3; фронтенд – React + TypeScript (Vite).
- Паролі зберігаються лише у вигляді bcrypt-хешів, доступ до API – за JWT-токеном.
- Документація API генерується автоматично (OpenAPI / Swagger UI).
- Розгортання однією командою через Docker Compose.
- Інтерфейс українською мовою.

## 1.6. Попередній вибір шаблонів проектування

Аналіз вимог показує місця, де доречні GoF-шаблони:

| Вимога | Проблема | Шаблон |
|---|---|---|
| FR-4 | Кілька алгоритмів розрахунку середнього балу, вибір у налаштуваннях | **Strategy** |
| FR-5, FR-8 | Після виставлення оцінки треба оновити борги, сповіщення, середній бал – не зв'язуючи сервіс оцінок з усіма ними | **Observer** |
| FR-3 | Послідовність незалежних перевірок перед збереженням оцінки | **Chain of Responsibility** |
| FR-1, FR-3 | Поведінка студента залежить від статусу, переходи між статусами обмежені | **State** |
| FR-7 | Усі звіти мають однаковий алгоритм (зібрати дані → агрегувати → оформити), різняться кроки | **Template Method** |
| FR-7 | Створення потрібного генератора звіту за типом | **Factory Method** |
| FR-7 | Покрокова побудова складного об'єкта звіту (заголовок, колонки, рядки, підсумки) | **Builder** |
| FR-3 | Єдина шкала оцінювання для всієї системи | **Singleton** |
| Кабінет студента | Одна точка доступу до оцінок, балу, боргів і розкладу студента | **Facade** |

Також застосовуються GRASP (Controller, Information Expert, Creator, Low Coupling, High Cohesion,
Pure Fabrication) та принципи SOLID – їх застосування описано в `docs/03-architecture.md`.
